## 一、缘起：为什么一个小学老师需要自己的「客厅」

前面几年做的网页学件越来越多，散在 D 盘、U 盘、微信文件传输助手里。上课要用，得先找；同行来问，得打包发；换一台机器，又得重新拷一遍。更麻烦的是**没有一个地方能说清"我到底做过什么"**——文件夹里躺着一堆 `index.html`，但那不叫作品集，那叫仓库杂物堆。

于是有了一个很朴素的念头：**能不能有一个网址，打开就是我做的东西；学生点开就能用，老师点开就能拿走。**

这件事的技术门槛不在"会不会写网页"，而在"知不知道往哪儿放、怎么让人打开"。GitHub 是英文界面，对不熟悉的人来说，每一步都像在陌生城市找路：不知道 Repository 是什么，不知道 Public 和 Private 差在哪儿，推上去没反应也不知道该查哪里。

这份手记就是那次找路的地图。**它不是 GitHub 教程，是一份"我自己走过一遍、把坑都标出来"的路线记录。**以后再建站点、再带学生做作品集，照着走一遍就行。

## 二、全貌：一套「客厅 + 房间」的架构

把整个站点想成一套房子，很多原本想不清的问题一下就清楚了。

```
【指路牌】顶栏：徽标 · 站名 · 分区导航 · 深浅色切换

【客　厅】index.html（总入口）
　　迎宾：一句话说清“这里是什么、给谁用”
　　分流：我是老师 → 成果 ｜ 我是学生 → 学件 ｜ 第一次来 → 说明
　　指示：快捷区（按打开次数自动排序）+ 搜索
　　说明：关于本站（是什么 / 怎么走 / 最近更新）

【房间 A】works/　专业成果（给老师看：讲座、手册、共建平台），4 件
【房间 B】learn/　学生学件（给学生用：点开即用），13 件

【门】每扇门都挂着「← 作品集」，点一下回客厅
```

**这套架构解决的核心问题，是"人找不到路"。**

- 客厅负责**说清自己是谁**：不看说明也知道这是符京雷的教学资源库，不是随便一个网盘。
- 客厅负责**分流**：老师不会误入学生学件，学生不用在讲座材料里翻找。
- 房间负责**只做一件事**：一个学件就是一节课，打开就能上。
- 双向门负责**不迷路**：进房间容易，回客厅也容易。

早期版本只有客厅、没有门牌（房间进去就出不来，只能按浏览器后退），这是最先暴露的问题，第七节详细讲怎么补的。

## 三、选型：为什么最后落在 GitHub Pages

做个人站点的路有很多条，当时把主流方案摆在一起比了一遍：

| 方案 | 成本 | 是否能用自己的域名 | 稳定性 | 上手难度 | 结论 |
|---|---|---|---|---|---|
| 国内博客平台（公众号/简书类） | 免费 | 否 | 中 | 低 | 排版受限，交互式学件跑不起来 |
| 网盘分享链接 | 免费 | 否 | 低（易失效、需登录） | 低 | 学生打不开，体验差 |
| 教育云盘/学校空间 | 校内免费 | 否 | 中 | 低 | 校外访问受限，家长用不了 |
| 云服务器 + 域名 | 约 100–300 元/年 | 是 | 高 | 高（要会运维） | 学习成本不划算 |
| **GitHub Pages** | **免费** | 可用 | **高（CDN 全球加速）** | 中（英文界面） | **采用** |

选 GitHub Pages 的关键理由有三条，都不是技术理由：

1. **免费且不掺水**。没有广告位、没有"升级会员解锁"，不会哪天弹出收费提示。
2. **纯静态，天然安全**。不需要数据库、不需要后台账号，也就不存在"被拖库"。上传的只有 HTML 本身。
3. **一套仓库天然是作品档案**。每次改动都有提交记录，哪天想把旧版本找回来，翻历史就行——这是任何网盘都给不了的。

它的代价也很明确：**英文界面**。这一点靠第四节的速查表解决。

## 四、先认字：GitHub 英文界面速查表

这是整份手记里最该先看的一节。不用背，遇到时回来查。

### 4.1 最常出现的九个词

| 英文 | 中文 | 用大白话说 |
|---|---|---|
| Repository（Repo） | 仓库 | 一个文件夹，你所有文件放里头，有历史版本 |
| Branch | 分支 | 文件夹的"平行版本"，`main` 是主版本 |
| Commit | 提交 | 拍一张快照，附一句说明，从此可以回到这一刻 |
| Push | 推送 | 把本机的快照传到 GitHub 上 |
| Pull | 拉取 | 把 GitHub 上的改动取回本机 |
| Clone | 克隆 | 第一次把整个仓库搬到本机 |
| Fork | 派生 | 把别人的仓库复制一份到自己名下（改别人的东西用） |
| Public / Private | 公开 / 私有 | 私有仓库**连网站都打不开**，这是最容易栽的坑 |
| GitHub Pages | 页面服务 | 把仓库里的 HTML 直接变成网站的功能 |

### 4.2 界面上真正要点的几个地方

| 位置 | 英文原文 | 干什么 |
|---|---|---|
| 仓库首页右上 | **Settings** | 所有配置的入口，最常来 |
| Settings 左侧栏 | **Pages** | 开启网站服务、看网址、看构建状态 |
| Settings 最底部 | **Danger Zone → Change visibility** | 私有转公开（转错就得来这儿改） |
| 仓库首页右侧 | **Releases / About** | 放简介、放链接 |
| 文件列表右上 | **Add file → Upload files** | 不会命令行时，直接网页上传也行 |
| 提交后 | **Actions** | 看自动构建是成功还是失败 |
| 仓库名旁 | **Public / Private** 标签 | 一眼看仓库是不是公开的 |

### 4.3 三个"看一眼就知道状态"的地址

记不住界面在哪时，直接在浏览器地址栏拼这几个地址，比翻菜单快：

| 想确认什么 | 打开这个地址 | 怎么判断 |
|---|---|---|
| 仓库是不是公开 | `raw.githubusercontent.com/用户名/仓库名/main/index.html` | 能打开就是公开，404 就是私有 |
| 网站服务有没有开 | `github.com/用户名/仓库名/deployments` | 有 `github-pages` 记录就是开了 |
| 网站有没有构建完 | 上面那条点进最新一条，看 state | `success` 才算真的上线 |

## 五、动手：从零到上线的七个步骤

下面这套流程，是这次真正跑通的顺序。**每一步都有"做完怎么确认"，不要跳。**

### 第 1 步：注册与建仓库

- 注册 GitHub 账号，用户名想好——它会出现在网址里，改起来麻烦。
- 新建仓库（New repository），仓库名有讲究：

| 你想要的网址 | 仓库名该叫什么 |
|---|---|
| `https://用户名.github.io/`（根路径，最干净） | **必须**叫 `用户名.github.io` |
| `https://用户名.github.io/项目名/`（子路径） | 随便起，比如 `diannao-diyike` |

> ⚠️ 只有名字完全等于 `用户名.github.io` 的仓库才占根路径。这次"客厅"就是 `lantu2026.github.io`，所以主站地址特别短；"电脑第一课"是另一个仓库，于是自动落在 `/diannao-diyike/` 子路径下。**两者互不干扰，各推各的。**

- 建仓库时那个 **`Keep this code private`** 复选框，**不要勾**。勾了之后网站一律打不开，而且报错是 404，不会告诉你"因为你设了私有"。

**确认方式**：仓库首页名字旁边显示 `Public`。

### 第 2 步：把本地文件整理成能上线的样子

- 顶层必须有一个 `index.html`，这是默认首页。没有它，根网址就是 404。
- 每个房间一个文件夹，文件夹里也要有自己的 `index.html`：

```
lantu2026.github.io/
├── index.html          ← 客厅
├── works/              ← 房间：专业成果
│   ├── shuzhi-funeng/index.html
│   └── ...
└── learn/              ← 房间：学生学件
    ├── photosynthesis/index.html
    └── ...
```

- **路径全部用小写英文加短横线**（`ai-literacy`），不要用中文名做文件夹。中文路径在网址里会变成一长串 `%E5%AD%A6...`，发给别人很难看，个别设备还会打不开。
- 文件名和网址是对应的：`learn/quiz/index.html` 对应的网址就是 `.../learn/quiz/`。

**确认方式**：本机双击 `index.html` 能正常打开，且从首页点进每个房间都能点通。

### 第 3 步：提交与推送

命令行三步走（在仓库文件夹里执行）：

```bash
git init                                  # 第一次才需要
git add -A                                # 把所有改动放进待提交区
git commit -m "首页新增电脑第一课入口"      # 拍快照，写清改了什么
git remote add origin git@github.com:用户名/仓库名.git   # 第一次才需要
git push -u origin main                   # 推上去（-u 记住，以后直接 git push）
```

如果不想碰命令行，GitHub Desktop 这类图形工具也能干同样的事，界面是"Fetch / Pull / Push"三个按钮。

**确认方式**：浏览器打开仓库页面，能看到刚推上去的文件。**推完不要凭感觉认为成功了**，第六节第 5 个坑专门讲这件事。

### 第 4 步：开启 Pages

1. 进 `Settings` → 左栏找 `Pages`
2. `Source` 选 **Deploy from a branch**
3. `Branch` 选 **main**，目录选 **/(root)**
4. 点 `Save`

保存后 GitHub 会自动构建一次，通常 30 秒到 2 分钟。

**确认方式**：回到 `Settings → Pages` 顶部会出现一行绿色提示，写着 `Your site is live at https://...`。没出现就等，别急着改配置。

### 第 5 步：等构建、验上线

构建是异步的，保存完立刻访问大概率还是 404。这时候查状态比反复刷新网页快：

```bash
# 看最近一次部署
curl -s "https://api.github.com/repos/用户名/仓库名/deployments?per_page=2"

# 看这次部署的状态（把 id 换成上一条返回的 id）
curl -s "https://api.github.com/repos/用户名/仓库名/deployments/{id}/statuses"
```

状态从 `queued` → `in_progress` → `success`。**看到 `success` 才算真的上线**，这时访问网址必定是 200。

### 第 6 步：逐个链接体检

站点能打开不等于每个房间都能打开。最省事的做法是把首页里所有链接抽出来，一条条 curl：

```bash
# 抽出页面里所有内部链接
grep -o 'href="[^"]*"' index.html | sed 's/href="//;s/"$//' | sort -u

# 逐条检查
curl -s -o /dev/null -w "%{http_code}\n" "https://用户名.github.io/learn/quiz/"
```

全是 `200` 才算过关。这一步这次抓出过真问题：首页漏了"电脑第一课"的入口，房间里面又都没有回客厅的路。

### 第 7 步：让每个房间都能回客厅

见第七节。这一步不做，邻居来串门会在房间里转晕。

## 六、踩坑记：八个真实故障与解法

这一节是整份手记最值钱的部分。**每个坑都真踩过，报错现象、真实原因、最终解法都记下来。**

### 坑 1：桌面工具报「认证失败」，其实是仓库不存在

**现象**：GitHub Desktop 提示认证失败，让人以为密码或密钥错了，反复重置 token 也没用。

**真相**：那个仓库在 GitHub 上根本还没建。本地已经设好了 `remote` 指向一个不存在的地址，工具跳过建仓库这步直接去连，于是报"认证失败"。

**解法**：先在网页上确认仓库真的存在，再配 remote。判断一条命令就够：

```bash
git ls-remote origin
# 返回 "Repository not found" = 仓库不存在（或没权限），不是密码问题
```

### 坑 2：`Failed to connect to github.com:443`

**现象**：`git push` 卡住然后报连接被重置，浏览器却能正常打开 github.com。

**真相**：HTTPS 的 443 端口在某些网络环境下会被中断，SSH 走 22 也常被拦。

**解法**：走 SSH over 443，让 SSH 走一个不容易被拦的端口：

```
# ~/.ssh/config
Host github.com
  HostName ssh.github.com
  Port 443
  User git
```

然后把 remote 从 HTTPS 换成 SSH：

```bash
git remote set-url origin git@github.com:用户名/仓库名.git
```

### 坑 3：网站一直 404，因为勾了「Keep this code private」

**现象**：文件明明推上去了，仓库页面也能看到，但网址打开就是 404。没有任何提示说明原因。

**真相**：仓库是私有的。**私有仓库的 Pages 对外一律不可见**，而报错和"没建站"完全一样。

**解法**：`Settings` → 拉到底 `Danger Zone` → `Change visibility` → 改成 Public。

**判断技巧**：不用登进去猜，直接探一下 raw 地址——能拿到内容就是公开，404 就是私有：

```
raw.githubusercontent.com/用户名/仓库名/main/index.html
```

### 坑 4：转成 Public 了，还是 404

**现象**：仓库已确认是 Public，`raw` 地址也 200 了，网站根路径仍然 404。

**真相**：**Pages 没启用**。用户主页仓库（`用户名.github.io`）不一定会自动开 Pages，需要手动配一次。

**解法**：按第五节第 4 步走一遍：`Settings → Pages → Deploy from a branch → main → /(root) → Save`。

**踩过的误判**：查 `api.github.com/repos/.../pages` 返回 404，被误读成"Pages 没开"。实际上**匿名查这个接口一律 404**，拿另一个确定已上线的仓库对照也是 404。有效判据是查环境：

```
api.github.com/repos/用户名/仓库名/environments
# 结果里出现 "github-pages" = Pages 已配置
```

### 坑 5：push 被打断，误以为已经推上去了

**现象**：命令敲了 `git push`，中途切走或被打断。回头看 `git status` 显示工作区干净，理所当然认为"推完了"。结果线上还是旧版本。

**真相**：**`git status` 只反映本地，跟远端没关系。**工作区干净只能说明没有未提交的改动，不能说明远端收到了。

**解法**：永远用哈希对比，这是唯一可靠的确认：

```bash
git fetch origin main
git rev-parse HEAD          # 本地最新
git rev-parse origin/main   # 远端最新
# 两个哈希一样 = 真的推上去了
```

这次就栽在这里：本地是 `262d6b2`，远端还停在 `d7becdb`，首页的"电脑第一课"入口在线上一直不存在。

### 坑 6：线上文件比本地小，以为内容丢了

**现象**：`enumeration/index.html` 本地 1,093,966 字节，线上抓下来少了十万多字节，怀疑传输丢失。

**真相**：两个叠加的假象。

- 一是 `.gitattributes` 里 `* text=auto eol=lf` 会把 Windows 的 `CRLF` 换行转成 `LF`，每次换行少 1 字节，文件大就少很多。这属于正常，不是损坏。
- 二是 `curl -m 20` 的超时截断。大文件在慢网络下 20 秒下不完，抓到的只是前半截。

**解法**：比对前先放宽超时，再按"本地字节数 − 换行符个数"核算：

```bash
curl -s -m 120 -o /tmp/a.html "https://用户名.github.io/learn/enumeration/"
wc -c < /tmp/a.html
```

**教训**：**大文件（大于 1MB）比对字节数，必须放宽 curl 超时**，否则截断会被误判成内容缺失。

### 坑 7：手机端"横向溢出"，其实是截图工具的假象

**现象**：用无头浏览器按 390px 宽截图，内容被切掉一块，看起来像横向溢出。

**真相**：Chrome 无头模式有最小视口限制（约 489px）。设 390 实际渲染宽度是 489，截图却仍按 390 裁——**假溢出**。

**解法**：截图宽度不要小于 500px；真要判断溢出，直接量数据：

```javascript
document.documentElement.clientWidth   // 视口宽
document.documentElement.scrollWidth   // 内容宽
// 两者相等 = 没有横向溢出
```

### 坑 8：给所有页面加返回按钮，结果越加越多

**现象**：写脚本批量为 16 个页面注入"返回作品集"按钮，跑一次正常；跑第二次又注入一遍，页面里出现两份、三份。

**真相**：注入用的开始/结束标记，我拿同一对标记包了两段内容（一个样式块、一个脚本块）。清理时正则从第一个开始标记匹配到第一个结束标记，只删掉前一段，后一段留下，再注入就又叠一层。

**解法**：**一段注入内容只用一对标记整体包裹**，清理时循环剥离直到没有：

```python
def strip_all(html):
    prev = None
    while prev != html:          # 一直剥到不再变化
        prev = html
        html = PAT.sub("", html)
    return html
```

**顺带得到的验收方法**：把注入后的页面剥掉那一段，**应当和原件逐字节一致**。一致才证明"只是加了一层，没碰原来的东西"。这次 16 个页面全部通过。

## 七、双向门：让「客厅」与「房间」互相找得到

这是这次改动的核心，也是"客厅"这个比喻真正落地的地方。

### 7.1 原来的问题

房间（子页面）是独立的单文件学件，各自有各自的配色、布局、代码。从客厅点进去很容易，**出来却只能按浏览器的后退键**。投屏上课时，老师退回首页再找下一个学件，中间要绕一大圈。

### 7.2 设计上的四个约束

直接在 16 个页面里各加一个按钮行不通，因为：

1. **不能改布局**。学件是按自己的版式调好的，插一行会挤乱。
2. **不能挡住内容**。学件左上角大多被 logo、标题占着（种植体验是绿色标题条、枚举算法是"算法实验室"标）。
3. **不能太吵**。课堂上投屏，一个大按钮比学件本身还显眼，是干扰。
4. **手机上要能用**。触屏没有 hover，靠"鼠标移上去才出现"的设计在平板上等于没有。

### 7.3 最后的做法

统一在**左下角**挂一枚半透明小胶囊：

| 属性 | 取值 | 为什么 |
|---|---|---|
| 位置 | 左下角，`fixed` | 各学件最空的区域；避开左上角 logo |
| 尺寸 | 高 32px，圆角胶囊 | 够点，不抢眼 |
| 默认透明度 | 0.9；触屏 0.95 | 浅色背景上仍看得清（试过 0.55，太淡） |
| hover / 键盘聚焦 | 完全不透明 + 轻微上浮 | 有反馈，知道能点 |
| 层级 | `z-index: 2147483000` | 学件里有全屏 canvas、固定工具栏，层级必须压过它们 |
| 打印 | `@media print` 隐藏 | 打讲义时不出现 |
| 快捷键 | `Alt + ←` | 键盘、触屏笔用户的另一条路 |

一个容易忽略的细节：**`display` 不能用 `inline-flex`**。胶囊里"← 作品集"和 `<b>` 加粗是分开的文字节点，`inline-flex` 会把每个节点当成独立项、按 `gap` 撑开，结果渲染成"我是 老师 ，要看方法"这种别扭间距。改成 `inline-block`，文字按正常排版流动才对。

### 7.4 怎么保证不出错

16 个页面靠手改不现实，于是写了一个脚本 `tools/inject-home-link.py`，只做三件事：

```bash
python tools/inject-home-link.py --apply    # 注入 / 更新
python tools/inject-home-link.py --check    # 只检查每页有几份标记
python tools/inject-home-link.py --revert   # 全部撤掉
```

验收标准定得很硬：**剥离注入内容后，与备份原件逐字节一致**。16/16 通过，才敢推。

### 7.5 独立仓库怎么办

"电脑第一课"是另一个仓库，不在主站里。它的课时页本来就有自己的"回课程首页"导航，所以只给它的两个首页加了指向作品集的按钮，**92 个课时页一个没动**——房间里的路本来就通，不需要再加。

**一条经验**：往别人的页面里加东西之前，先看它自己有没有路。有就不动，没有才补。

## 八、红线：教学资源上公网的隐私边界

这条比技术重要。

### 8.1 定死的三条线

| 内容 | 处理 | 原因 |
|---|---|---|
| 学生姓名、学号、成绩 | **不上线** | 未成年人个人信息，一旦公开无法撤回 |
| 家长联系方式 | **不上线** | 同上 |
| 校内教职工通讯录（手机号） | **不上线** | 同事的联系方式不是我能替他公开的 |

### 8.2 已经做到的程度

- 全部 13 件学生学件**不采集任何个人信息**，打开即用，不登录、不填名字。
- 需要班级数据的工具（点名、评价、班务工作台）**只在校内网用**，不进这个仓库。
- 学件里的案例人物全部为虚构，页脚明确写清："本站所有学件均不含学生姓名、学号、成绩、家长联系方式等个人信息"。

### 8.3 一条诚实的提醒

纯前端网页上的"口令保护"**不是安全边界**。页面上设个密码，它只挡住路过的人，挡不住真会看源码的人——口令比对逻辑就在文件里，谁都能翻出来。

所以判断标准不该是"我有没有加密"，而是：**这段内容被全网看到，我能不能接受。**能接受才放上去，不能接受就不放，别指望前端的密码。
